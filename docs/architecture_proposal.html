What actually needs building

The target architecture is the right shape. But it is written as if the library does not exist yet, and most of it does — under different names, in jax_harness/pi_*. Three decisions have to be made before any code moves.

Keep the architecture. Change how it is described, and settle three things first: there are two model adapters where the plan assumes one; the package path the plan targets is already occupied by an older generation of code; and the analysis boundary is drawn one word too tightly — model-free and jax-free are not the same rule, and three headline producers sit in the gap.

Nothing below argues against the design. The mapping is a scoping correction: roughly half of §3 is promotion and naming work, not implementation.

The three decisions

1 · There are two model adapters, and this is the real work

The plan assumes one ModelAdapter. The harness has two, built at different times for different jobs, and both are load-bearing.

pi_core.py — joltz/Boltz-2 trunk. 19 importers. Produced every headline capture (exp_gym2 → gym2s_*.npz).
pi_models.py — mosaic adapter over boltz2 / of3 / protenix / af2. 3 importers. The cross-model work only.

The newer one is the better interface: a registry, lazy backend imports, and a normalized output schema — it already states the plan's own rule in its docstring (“extractors may be model-specific, analysis must not be”). But it carries almost none of the traffic, and the one that carries the traffic is the one that produced the results we just verified.

Proposal: make pi_models's interface the contract, and add a Boltz-2/joltz adapter that wraps pi_core unchanged. Unifying by rewriting would rewrite the code behind the headline, which §1 already forbids (“do not rewrite validated numerical kernels”).

2 · The package path is already occupied

§3 puts the library at src/protein_interpretability/. That directory is not empty — it is the installed package, and it holds an entire earlier generation of the project.

pyproject: package-dir = {"" = "src"} — so import protein_interpretability gives you this, and none of the current science.
contents: extractor_boltz, extractor_esmfold, extract_attention, msa_analysis, attribution/, rsa/, scoring/, esm_head/
plus 14 MB of notebooks inside the package directory
last touched 2026-05-20 — dormant three months

So the repository holds two generations that have never met: a package-shaped ESM and Boltz-torch layer that nothing current imports, and a flat directory of 100 scripts that does all the science and reaches its own modules through sys.path.insert — 63 files do this.

Proposal: reclaim the name for the new library, move the notebooks out of the package, and keep attribution/ — it is well-built torch/Boltz-2 gradient plumbing and phase 6 (the ESMFold and AF2 audit) is the natural place to judge it. Mechanical work, no scientific risk, and it unblocks everything else.

3 · Model-free is not jax-free

§10 promises offline analysis “installs and runs without model-specific environments”. That is achievable — no analysis script loads a model — but only if the rule is written about backends and weights rather than about JAX.

68 of 100 files import no model stack at all.
Of the 32 that do: 25 load a model, 2 take a pre-loaded one, and 5 use jax purely as accelerated linear algebra.
Top-level import jax, no model: analyze_svd, analyze_pc2, analyze_layer_match — all three are report producers.
Function-local: analyze_transfer (behind --k-sweep), pi_basis (float64 SVD).

Written as “no jax”, three headline producers cannot live in analysis/. Separately, the boundary does not exist operationally yet at all: run.sbatch and analysis.sbatch execute in the same mosaic container, so the plan's Analysis gate is currently unverified rather than passing.

Proposal: state the contract as “analysis imports no model backend and loads no weights; jax as a numerics library is allowed”, and enforce it with an import-guard test written the way pi_archive_test is — asserting the refusal, not the happy path.

Two things that will bite during the work

Cohorts have no manifest, so the collection API has nothing to read

§6 opens with Cohort.from_manifest("configs/cohorts/cross_model_assays.yaml"). No such file exists, and no cohort file exists anywhere in the repository. Today launch_gym2s.sh iterates for f in $W/runs/gym2_*.npz — the identity of the twelve assays is whatever a previous sweep happened to leave on disk. The §5 manifest work is a hard dependency of the §3 collection surface, not a parallel track.

Changing how scripts are invoked breaks the regression harness

The check built today reruns each of the 17 report producers from the argv recorded in its own archive. That is the only mechanism we have for proving old and new agree, and it depends on those command lines staying runnable. Keep script-level argument compatibility through the migration, or record a translation alongside the CLI.

Proposed order of work

Ordered so that each step is verifiable by the harness before the next one starts, and so the risky step comes after the boundaries are settled rather than before.

  1. Reclaim the package path

    Move the dormant generation and lift the notebooks out of the package. No science touched, and nothing else can be placed until the name is free.

  2. Write the schema that is already cited

    records.py / outputs.py. The normalized dict returned by pi_models.run_one is the de-facto schema; pi_schema.py is referenced in a docstring but has never existed in any commit.

  3. Promote pi_* into the package

    Thin re-exports first, jax_harness still importable, no behaviour change — then re-run the 17 producers and expect exact zeros, allowing the known analyze_svd non-determinism band.

  4. Unify the adapters

    pi_models's interface becomes the contract; the Boltz-2 adapter wraps pi_core rather than replacing it. This is the step with real scientific risk, so it happens with the boundaries and the harness already in place.

  5. Then the CLI and the first experiment scripts

    The vertical slice the plan wants judged at the API gate — and the first honest test of whether the surface is actually easy to read.

Edits I would make to the plan itself

  • Annotate the §3 tree with what already implements each module, so it stops reading as greenfield and the scoping is visible.
  • Move records.py to the front of the collection list — it is cited by existing code as though it were already there.
  • Reword the offline-analysis rule in §9 and §10 to name backends and weights rather than environments in general.
  • Consider folding prediction/ into collection/. One adapter call already returns representations and predictions together; two packages with two runners would duplicate the same forward pass.
  • Say explicitly that §5's manifests block §3's collection API, rather than listing them as a later phase.
