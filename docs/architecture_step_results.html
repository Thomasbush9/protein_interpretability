The adapters disagree

The package path is reclaimed, six modules are promoted, and all 17 report producers still reproduce exactly. The one thing that did not go to plan is the thing you asked to have checked: pi_models and pi_core do not produce the same Boltz-2.

Steps 1–3 are done and verified. The adapter question now has a measured answer. pi_models builds Boltz-2 with the MSA subsampled to 1,024 rows where pi_core uses the whole alignment. Measured across two assays, that costs essentially nothing scientifically — the mutation signal survives at correlation 0.998, which is no worse than two subsample draws agree with each other.

What it costs is exactness. The full alignment reproduces dz_site bit-for-bit across keys; the subsample does not. Since every archived capture was made without subsampling, keeping the full alignment is worth about four lines of code — but this is a reproducibility call, not a scientific one, and the numbers support either choice.

It is the MSA regime, and your own docstring predicted it

Introspecting the two built models:

pi_models wrapper.model.msa_module.subsample_msa = True, num_subsampled_msa = 1024
pi_core load_model(subsample_msa=False)

pi_core.load_model already says this in words — “deliberate and differs from mosaic's design-time default: for interpretability we need the MSA depth to be an exact, controlled quantity, not a random 1024-row draw that changes per key.” What is new is the price: 0.27 Å on expected distance.

It does not show up as an input difference, which is what makes it dangerous. Depth in the features matched at 6,857 on both sides; the subsampling happens inside the MSA module, downstream of featurisation, where a depth check does not look.

The confirming experiment: cap the alignment at 894 rows, below the 1,024 threshold, so there is nothing to subsample. The disagreement collapses.

So is the subsample good enough? Measured: yes on accuracy, no on exactness

The follow-up experiment varies only the flag — both arms through pi_core and the same capture code, so the adapter is not confounded with the regime the way the comparison above was. Two assays, 32 variants each. Because exp_gym2 caps alignments at 2,048 rows, both arms are a 2,048 → 1,024 draw regardless of the protein's native depth.

The quantity that decides it is dz_site — the variant-minus-wild-type difference the shared basis is built on. Every result in the project is a difference, and a random draw that moves between the two halves of a pair lands in dz_site as though the mutation had caused it. So the comparison that matters is not full-vs-subsample on its own, but full-vs-subsample against subsample-vs-subsample:

dz_site comparisonARGRCATRReading
full vs subsample0.99800.9987the regime change
subsample vs subsample0.99710.9983the noise floor — re-drawing alone
full vs full, new key—1.000000with no subsampling the key changes nothing

The regime change costs no more than re-drawing does. There is no systematic bias; the whole discrepancy is draw variance. Wild-type structure at matched key is effectively unchanged — CA distance matrix 0.022 Å mean, pLDDT within 0.011 — and the endpoint Spearman moves by about 0.02 with no consistent sign, far inside the estimation error at n=32.

The control arm earned its keep

The first run showed a 9.8 Å coordinate spread, which looked like the subsample moving the structure. It was not. Coordinates come from the diffusion sampler, which is stochastic and keyed by the same seed the MSA draw uses, so arms at different seeds changed both at once. Adding a full-alignment arm at a different key — where subsampling cannot act — separates them:

full vs full_key1 CA max 2.964 Å, mean 0.4431, pLDDT corr 0.9421
full vs sub_key1 CA max 2.949 Å, mean 0.4405, pLDDT corr 0.9468

Indistinguishable. All of the coordinate variation is the sampler; none of it is the alignment. Worth remembering as a general trap: never compare structures across different PRNG seeds and attribute the difference to whatever else you changed.

What it does cost is reproducibility

With the full alignment dz_site is bit-reproducible across keys — correlation exactly 1.000000, and the endpoint Spearman identical to four decimals. Under subsampling it is not. Adopting the subsample converts a deterministic collection step into a stochastic one at the ~1e-3 level.

That matters here more than the accuracy question does, for two specific reasons. Every archived capture was produced with subsample_msa=False, so old-versus-new comparisons would inherit draw noise rather than the exact zeros the regression harness currently returns. And this session has just spent real effort establishing which producers are bit-stable and which are not — adding a new source of irreproducibility to the collection step runs directly against that.

Recommendation: keep the full alignment. Not because the subsample is inaccurate — it is not, and by the accuracy criterion alone it would be fine to adopt — but because the fix costs about four lines and buys exact reproducibility against every existing archive. If you would rather take the simpler adapter and accept stochastic captures, the measurements above support that too; it is a reproducibility decision, not a scientific one.

Fixable, but not through the constructor

Step 4: the loader unification, verified

pi_core.load_model(backend="mosaic") now returns pi_models.load("boltz2", msa=…) unwrapped. That works because mosaic's wrapper holds exactly the joltz network in .model, so the trunk instrumentation is untouched — the unification is a swap of the loader, not a rewrite of the capture code.

The verification measures dz_site rather than the wild-type output, because every result here is a variant-minus-wild-type difference taken from the trunk. It reads the result against a scale rather than against zero: the same loader at a different key is the deterministic floor, and the 1,024-row subsample is a band this project has already accepted.

The mosaic loader sits at the deterministic floor — indistinguishable from the same loader run at a different key, with the endpoint identical to four decimals. The 0.030 Å residual visible in the wild-type distogram does not propagate into dz_site at all, because a small offset common to variant and wild type cancels in the difference. That is exactly why the test had to be on dz_site and not on the output.

Recommendation: the swap is safe for the representation results, but the default stays joltz. Captures also store absolute quantities — kl_glob, disto, plddt, ca — and those do carry the 0.030 Å difference. Making mosaic the default should follow a capture-level comparison of those fields, not ride along with this one.

Step 5: the CLI, scoped to what is stable

The plan sketches collect / predict / intervene / analyze. Those wrap code that is still moving. Three things are already stable, load-bearing, and were being done with a throwaway script each time — which is where tolerances and the known-unstable list get lost.

  • pi reproduce RESULT.json — replays the argv the result recorded, redirecting --out. Every archive already carries its exact command; this stops that from being re-implemented per investigation.
  • pi verify OLD NEW — the diff with the measured non-determinism bands applied, each band carrying how it was measured. An unknown producer must be exact, and the failure text tells you to run the unchanged code twice first.
  • pi inspect FILE.py — module-scope backend imports and results written with no protocol block. Across the 17 producers it flags exactly one: probe_gate, which imports equinox at module scope and does load a model.

None of the three imports numpy, jax or a backend, so all run on a login node — and inspect exists to hold other files to that. Its first version checked for a module-level PROTOCOL constant and flagged four producers that have carried a protocol block in every archive they have ever written; they build it inline inside main. A guard that fails on the good path is worse than no guard, because the response is to stop reading it.

What else changed

  • The package path is reclaimed. The May-era generation is gone — 41 package files including 14 MB of notebooks, plus the 11 scripts/ files that imported it, the 5 launchers whose drivers those were, and 9 tests. Recoverable with git show fcceb3f:<path>.
  • Six modules promoted — statistics, basis, chemistry, metrics, protocol, and the archive seam. Each keeps a six-line alias in jax_harness, so roughly 60 call sites work untouched and the move could be verified before anything was rewritten.
  • records.py exists now. pi_models has cited it as pi_schema.py since it was written; it had never existed in any commit. Its checks are the three models' real divergences — bin grids that differ while bin counts match, per-atom versus per-token pLDDT, the unsqueezed sample axis. 25 tests pass, all of them asserting a refusal.
  • A provenance bug, caught by the move. build_master_report hashed a flat list of jax_harness basenames as its code identity. After the promotion that would have hashed the six-line pi_protocol alias and reported it as the identity of every protocol block on the page. The list is repo-relative now.
  • checkout.sbatch runs the repository instead of the mirror, which is what verifying a moved library requires — and what the plan's acceptance test (“jobs submitted from a clean checkout”) already asked for.

Where this leaves the sequence

Steps 1 through 3 are complete and verified. Step 4 — unifying the adapters — now has a concrete blocker rather than an open question, which is the useful outcome: the equivalence check you asked for found something a code review would not have.

My recommendation is to make the eqx.tree_at fix so pi_models runs the full alignment, then rerun exp_adapter_equiv.py and treat the remaining 0.003 Å mean as the tolerance decision. That residual is not the MSA and not the recycle count, and it is worth understanding before pi_core stops being the thing that produces captures — small systematic shifts are exactly what the shared basis measures.
